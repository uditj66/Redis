🔑 Strings & Keys — The Foundation of Redis

Redis is, at its core, an in-memory key-value store. Every value lives under a unique key. The simplest (and most common) value type is a String.

💡 Core Concepts

SET key value

Store any string value under a key. Overwrites if key exists.

GET key

Retrieve a value. Returns nil if key doesn't exist or expired.

EXPIRE key seconds

Set a time-to-live. Key auto-deletes after N seconds.

TTL key

Returns remaining time. -1 = no expiry, -2 = key gone.

📡 Pub/Sub — Real-Time Messaging

Pub/Sub is a fire-and-forget messaging pattern. Publishers send messages to channels without knowing who listens. Subscribers receive messages in real-time. Messages are NOT stored — it's purely real-time.

💡 Key Concept

Publisher
PUBLISH chat "Hello!"
→
Redis
Channel: chat
→
All Subscribers
SUBSCRIBE chat

⚠️ If no subscribers are listening, the message is lost forever!

🔴 LIVE

🧪 Experiment — Answer to Q2: What does PUBLISH return with 0 subscribers?

PUBLISH can be called independently of SUBSCRIBE. You don't need to be subscribed to publish. Redis always returns the number of subscribers who received the message. Use a channel nobody is listening to → Redis returns 0.

🚦 Rate Limiting — INCR + EXPIRE Pattern

One of the most elegant Redis patterns: use atomic INCR to count requests and EXPIRE to define the time window. No race conditions, no locks needed — Redis handles atomicity natively.

💡 Fixed Window Counter Pattern

key = "ratelimit:api:{user}:{window}"

count = INCR key          # atomic increment
IF count == 1:
    EXPIRE key 60         # set 60s window on first request
IF count > 10:
    RETURN 429            # Too Many Requests
ELSE:
    RETURN 200            # OK, proceed

🌸 Bloom Filter — Probabilistic Membership Testing

A Bloom Filter is a space-efficient probabilistic data structure that tells you whether an item is definitely NOT in a set, or possibly in it. Redis makes it trivial to implement with SETBIT and GETBIT — storing 2048 bits in just 256 bytes.

💡 Core Concepts

SETBIT key offset 1

Set a single bit at a position. Used when registering an item into the filter.

GETBIT key offset

Read a single bit. Used when checking membership. Returns 0 or 1.

BITCOUNT key

Count total bits set to 1. Used to compute the fill ratio and estimate false positive rate.

Pipeline (k × GETBIT)

All k hash positions are read in a single pipeline for O(k) performance with one round-trip.

⚙️ How a Bloom Filter Works

1
Hash the item with k different functions
→
2
Each hash gives a bit position [0, m)
→
ADD
🟣 SETBIT all k positions to 1
|
CHECK
🔍 GETBIT all k positions — any 0 = definitely absent

⚠️ All bits = 1 only means possibly present — hash collisions can cause false positives. There are zero false negatives.

⚠️ False Positives vs False Negatives

The most critical property to understand about Bloom Filters.

✅ Zero False Negatives

If any bit is 0, the item was never added. This is a guaranteed true negative — no exceptions possible.

⚠️ Possible False Positives

If all k bits are 1, the item is possibly present — but other items' hashes may coincidentally occupy those positions.

🚫 No Deletion Support

You can't flip bits back to 0 — that would corrupt other items. Use a Counting Bloom Filter if deletion is required.

📐 FP Rate Formula

Estimate the false positive rate for any filter configuration.

FP Rate = (1 − e−kn/m)k

m = bit array size (2048)
k = hash functions   (4)
n = items inserted
